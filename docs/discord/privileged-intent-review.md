## 1. 結論：申請すべきインテントは何か

コードを実地調査した結果です。**使っていないインテントを申請に含めると、申請全体が却下されます**
（Discord は部分承認をせず、1つでも不要と判断されると全体が Denied になります）。

| 特権インテント | 実際の使用 | 申請 | 根拠 |
|---|---|---|---|
| **Server Members** (`GUILD_MEMBERS`) | **使用中** | **申請する** | `src/bot/index.js:65` で有効化。参加/退出/キック/ニックネーム/ロール変更ログの根幹 |
| **Message Content** (`MESSAGE_CONTENT`) | **使用中**（実機確認済み） | **申請する** | 削除/編集メッセージの本文ログに必須。詳細は 1.1 |
| **Presence** (`GUILD_PRESENCES`) | **使用中** | **申請する** | メンバーのカスタムステータスの変更を検知してログを出力するため |

### 1.1 Message Content は本番で動作している（実機確認済み）

削除ログに実際のメッセージ本文が出力されることを確認済みのため、**本番のロボポリスは
ゲートウェイで MESSAGE_CONTENT (`1 << 15`) を要求できています**。したがって Message Content は
「実使用中の特権インテント」であり、申請対象で確定です。

一方で、**このリポジトリの内容そのままでは Message Content を要求できません**（申請とは別件の乖離）：

- `src/bot/index.js:60-68` の intents 配列に `messageContent` が無い
- `package-lock.json` が固定している Eris は `curtisf/eris` の commit `c075c5b`（`0.16.2-dev`）で、
  この版の `lib/Constants.js` の `Intents` は `directMessageTyping` (`1 << 14`) で終わっており、
  `messageContent` の定数が存在しない
- `lib/Client.js:176-188` は配列を走査して未知の名前を `warn` して**黙って捨てる**実装のため、
  仮に `'messageContent'` を配列に足しても無視される

この状態で計算されるビットフィールドは `719`（`messageContent` の `32768` を含まない）です。
実機が動いている以上、**本番環境は別バージョンの Eris か、別の intents 指定で稼働しています。**
（Developer Portal 側でも MESSAGE CONTENT INTENT は ON であることを確認済み。2026-09-13）

> **申請への影響：なし。** Message Content を申請対象に含めてください。
> ただし「リポジトリの `master` と本番デプロイが乖離している」こと自体は別途確認を推奨します
> （このリポジトリから `npm ci` で再デプロイすると本文ログが壊れます）。

## 2. 各インテントの使用箇所（審査で問われる根拠）

### Server Members Intent

| 機能 | ファイル |
|---|---|
| 参加ログ（アカウント作成日・使用された招待コードの特定） | `src/bot/events/guildMemberAdd.js` |
| 退出／キックログ（Audit Log 照合で退出とキックを判別、所持ロールを記録） | `src/bot/events/guildMemberRemove.js:14-16`（ロール記録）, `:28-31`（Audit Log 照合） |
| ニックネーム変更・ロール変更・メンバー認証通過ログ | `src/bot/events/guildMemberUpdate.js` |
| 他の全ログ埋め込みでの表示名／ニックネーム／アバター解決 | `src/bot/events/messageDelete.js:39-42`, `messageUpdate.js:16` |
| `/userinfo` コマンド | `src/bot/slashcommands/userinfo.js` |
| BAN / BAN解除ログの対象者情報 | `src/bot/events/guildBanAdd.js`, `guildBanRemove.js` |

**代替不可の理由**：`GUILD_MEMBER_ADD` / `REMOVE` / `UPDATE` は特権インテント無しでは一切届きません。
スラッシュコマンドは「ユーザーが実行したとき」しか動かないため、参加・退出という*受動的イベント*の記録には原理的に使えません。

### Message Content Intent

| 機能 | ファイル |
|---|---|
| メッセージをAES-256暗号化してDBへ保存（削除時ログの元データ） | `src/db/interfaces/postgres/create.js:42-64` |
| 削除メッセージの本文表示 | `src/bot/events/messageDelete.js:44-60` |
| 編集の Before / After 差分表示 | `src/bot/events/messageUpdate.js:60-110` |
| 一括削除ログ | `src/bot/events/messageDeleteBulk.js` |
| `/archive`（モデレーターによるチャンネル書き出し） | `src/bot/slashcommands/archive.js:36` |

**代替不可の理由**：削除されたメッセージは Discord API から再取得できません。
モデレーターが荒らし・詐欺リンク・ハラスメントに対処するには、削除される*前*に本文を保持している必要があり、
これはスラッシュコマンドでは実現できません。

### 3.5 判断が必要な項目：オプトアウトの設問

「ユーザーはメッセージ内容データの追跡をオプトアウトできますか？」は Yes/No のプルダウンのみで、
**その場に説明欄がありません**。

- **No（推奨）** — 事実そのままです。メンバー個人が自分だけログ対象外になる仕組みはありません。
  補足は「なぜMessage Content Intentが必要ですか？」欄に書きます（上記の文面に含めてあります）。
- **Yes** — 「管理者が /ignorechannel と /stoplogging で制御できる」ことを根拠にする解釈ですが、
  これは**サーバー単位の制御であってユーザー個人のオプトアウトではありません**。過大申告と
  受け取られた場合、送信時に同意する「情報が正確かつ完全である」という表明に反します。

**推奨は No です。** 監査ログBOTで個人がログを免れられないのは機能の性質上当然であり、
当方が運営するサーバーのみで動くプライベート運用という文脈では説明可能です。

## 8. データ保持の実装と Railway での運用

### 8.1 何を消しているか

| 対象 | 期限 | 実装 |
|---|---|---|
| PostgreSQL `messages` の行（削除・編集ログの出力先があるサーバーのみ保存） | `MESSAGE_HISTORY_DAYS` 日（既定30） | `src/miscellaneous/prune.js` |
| 単一削除されたメッセージの行 | 削除がログ出力された時点 | `src/bot/events/messageDelete.js:20` |
| PostgreSQL `guilds` の行 | BOTがサーバーから離脱した時点 | `src/bot/events/guildDelete.js:8` |
| Redis の招待／Webhook／設定キャッシュ | 3時間 | キー設定時の `EX` |

### 8.2 実行方式は2択（どちらか一方）

**方式A: BOT内で定期実行（既定・設定不要）**

shard 0 を持つワーカーが起動時に1回、以降1時間ごとに掃除します。`MESSAGE_HISTORY_DAYS` を
設定するだけで有効になります。Railway の変数に `MESSAGE_HISTORY_DAYS=30` を入れれば完了です。

**方式B: Railway の Cron サービス**

1. Railway のプロジェクトで **New Service → GitHub Repo** から同じリポジトリを追加
2. Settings → **Custom Start Command** に `node src/miscellaneous/prune.js`
3. Settings → **Cron Schedule** に `0 4 * * *`（UTC。毎日13時JST）
4. Variables に Postgres の変数を参照で設定（`${{Postgres.PGHOST}}` など）＋ `MESSAGE_HISTORY_DAYS=30`
5. **BOT側のサービスに `PRUNE_EXTERNAL=true` を設定**して、BOT内の定期実行を止める

`prune.js` は単体実行時に削除件数を出力して `exit 0` で終了するので、Railway Cron の
「実行して終了する」モデルに適合します。

> Railway の Cron は、前回の実行がまだ動いている場合は新しい実行を開始しません。初回の大量削除で
> 1時間以上かかるような場合でも、次回実行が重なることはありません。

**推奨は方式A**です。サービスが1つ増えず、変数の二重管理も不要で、BOTは常時起動しているためです。

### 8.3 保持期間を過ぎたメッセージの扱い

行が消えた後でも、**イベントが起きた事実は記録されます**（内容だけが出ません）。

| 操作 | 30日以内 | 30日経過後 |
|---|---|---|
| メッセージ削除 | 本文付きでログ出力 | 「削除された」ログを出力。Content 欄は「保持期間を過ぎているため取得不可」、日時とメッセージIDは表示 |
| メッセージ編集 | Before / After を出力 | 「編集された」ログを出力。Previous 欄は取得不可、投稿者・チャンネル・ジャンプリンクは表示 |
| 一括削除 | paste へ書き出してリンク | 「N件が一括削除された、内容は保持期間外」を出力 |

実装は `src/bot/utils/retention.js` の `isBeyondRetention()` です。メッセージIDの snowflake から
送信時刻を復元し、`MESSAGE_HISTORY_DAYS` を超えているかを判定します。

**「保持期間切れ」と「そもそも記録していない」を区別しています。** 行が無い原因は2つあり、
前者だけをログに出します。後者（`/logbots` が無効なときのBOTメッセージ、AutoMod のアクション、
BOT導入前や停止中のメッセージ）まで出すと、古い削除のたびにノイズが出てしまうためです。
`MESSAGE_HISTORY_DAYS` が未設定のときは削除自体が走らないので、この判定は常に false になります。

**モデレーション上の意味**: 31日以上前の発言を削除しても、内容は残りませんが**削除された事実は残ります**。
保持期間を延ばせば内容も残せますが、31日以上にするとフォームの「30日以内か」に Yes と答えられません。

### 8.4 初回実行時の注意

これまで一度も削除していないため、初回は**全期間分の古い行**が対象になります。`prune.js` は
5,000行ずつ、1回の実行あたり最大100万行までに制限しているので、バックログが大きい場合は
数回の実行に分かれて消化されます。Postgres のディスク使用量が段階的に下がることを確認してください。

大量削除後は、必要に応じて `VACUUM (ANALYZE) messages;` を実行すると領域が回収されます
（Railway のデータベースには autovacuum があるため、通常は不要です）。
